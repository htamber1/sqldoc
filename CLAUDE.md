# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`sqldoc` is a **SQL Server infrastructure platform** (as of v2.0.0): it began as a database documentation CLI and now covers instance-level and infrastructure monitoring too. It connects to a database, extracts schema metadata, uses an LLM to generate plain-English descriptions, and renders self-contained HTML — and it also monitors the whole SQL Server instance. It has grown into a **twenty-three-command**, **17-dialect** platform (plus a VS Code extension and a REST API). The CLI is a command group: **`sqldoc doc`** (documentation), **`sqldoc scan`** (PII/compliance scan), **`sqldoc scan-files`** (PII-scan staged DDL text, no DB), **`sqldoc install-hooks`** (git pre-commit PII gate), **`sqldoc health`** (DMV performance/health + unused-objects detector), **`sqldoc quality`** (aggregate data profiling), **`sqldoc intel`** (schema intelligence + linked-server network mapping), **`sqldoc insights`** (AI-powered: NL-to-SQL, anomalies, glossary, relationship inference), **`sqldoc comply`** (HIPAA/GDPR/PCI-DSS reports, data lineage, per-principal access audit, cross-database board report), **`sqldoc executive`** (plain-English CTO/CISO summary), **`sqldoc dbt`** (unify dbt model metadata with the live schema), **`sqldoc server`** (instance-level health + SQL Agent jobs + backups + tempdb), **`sqldoc logs`** (ERRORLOG reader), **`sqldoc secure`** (security vulnerability scanner + score), **`sqldoc waits`** (wait-statistics analysis + AI), **`sqldoc ha`** (HA/replication monitoring), **`sqldoc deadlocks`** (deadlock analysis + SVG + AI), **`sqldoc plans`** (query execution-plan analyzer + AI), **`sqldoc capacity`** (capacity planning from agent history), **`sqldoc baseline`** (performance baseline + anomaly detection), **`sqldoc audit`** (audit-trail query/export), **`sqldoc serve`** (local JSON REST API, now with `--multi-tenant` + SSO), and **`sqldoc agent`** (persistent background monitoring daemon, now incl. server/backup/HA/tempdb + AI natural-language alerts + scheduled weekly email digest); a `DefaultGroup` routes `sqldoc <options>` (no subcommand) to `doc` for backward compatibility. AI runs through a unified `ai.dispatch` over four backends — **Ollama / Anthropic / OpenAI / Gemini** (`--ai-backend`) — with optional `--industry` vertical tuning. Entry point is `sqldoc.cli:cli`.

### v3.1.0 — SQL Server 2016 support, complete schema-change detection, honest errors
A **purely additive** release: nothing changes behaviour by default and no existing pipeline breaks on upgrade. The minor bump is for new functionality (an opt-in flag, new detection, a new snapshot format), **not** a break. **+89 tests (1446 → 1535)**. Full detail in `CHANGELOG.md`.

- **SQL Server 2016 works again.** `STRING_AGG` (trigger metadata) and `TRIM` (`quality` blank counts) are both **2017+**. The trigger query is **not** isolated — a parse error there aborts all of `extract_metadata`, so on a 2016 instance `doc` returned *no metadata at all*. Now `STUFF(... FOR XML PATH(''))` and `LTRIM(RTRIM(...))`. **`tests/test_sqlserver_version_floor.py` structurally scans the codebase for unguarded version-gated built-ins** — keep that list current when adding SQL. `APPROX_COUNT_DISTINCT` stays allowed *because* it sits behind a runtime probe; that is the pattern to copy.
- **Query errors are no longer labelled connection failures.** The connecting commands wrap *extraction*, not just `connect()`, so a rejected statement hit the same handler as a dead host and printed `Connection failed:` — which is how the 2016 bug presented, sending debugging toward firewalls and ODBC drivers. `cli._is_query_error` classifies by SQLSTATE (`08`/`28`/`IM` → connection; `42`/`S0`/`37` → query) and Msg 195 is explained as the version problem it is. **Deliberately conservative: anything ambiguous keeps the connection wording.** Do not widen this on a guess.
- **Schema-change detection was missing four kinds of change**, all of them captured in the snapshot and then never compared: column **width/precision** (so *narrowing* a column — data loss — reported no drift; `max_length` can't separate `decimal(10,2)` from `decimal(18,4)`, both 9 bytes), **indexes** (add/drop/key-change/uniqueness), and **FK retargeting**. `Column` gained `precision`/`scale` (optional, `None` default → adapters that don't report them behave exactly as before).
- **Snapshot format v1 → v2.** The straddling run suppresses *type* deltas only (else every sized column reports spurious drift), prints a note, and rewrites the snapshot; all other change kinds still report normally. Snapshots are a local artifact, not a published contract.
- **Index changes in generated migrations are review comments, not DDL** — the snapshot records constraint-backing indexes under the *constraint's* name, so `CREATE/DROP INDEX` would collide with the `PRIMARY KEY`/`UNIQUE` statements the generator already emits for the same object. **Don't "improve" this into real DDL without solving that collision first.**
- **`--fail-on-partial`** on all eleven `--cms`-capable commands: a fan-out covering 5 of 9 servers exits 0 by default (unchanged), or 2 with the flag. **Default off on purpose** — flipping it would break every existing pipeline. Honoured on all three estate paths (bulk, `executive --cms`, `access review --cms`) via shared `cli._exit_on_partial`; a flag that silently no-ops on two of three is worse than no flag. **`access review` declares its CMS options by hand rather than via `cms_bulk_option`** — a structural test in `tests/test_cms_fanout_defects.py` catches that divergence (it did, during this release).
- **Estate reports no longer overwrite single-DB reports.** Every `--cms` command declares a non-None `--output` default, so the `cms-<command>.html` fallback was dead code (`access review --cms`'s estate fallback was *literally the same string* as its single-DB default). `cli._cms_output` treats "still equal to this command's single-DB default" as "not explicitly set". **Tradeoff: explicitly passing `--output documentation.html` on a `--cms` run is also redirected.** The clean fix is `None` click defaults resolved per-mode across ~9 signatures.
- **`doc --format json` key sets are now pinned** (`tests/regression/test_contracts.py`). `build_json` uses `dataclasses.asdict`, so **any** field added to the model reaches the published export with no per-field review — which is exactly how `precision`/`scale` got there. `schema_version` stays `1` (additive, null-defaulted).

### v3.0.4 — enterprise field fixes: driver override, access-suite correctness, backup staleness
The **second release driven entirely by running sqldoc against real corporate infrastructure**, and the first to reach the paths v3.0.3 never touched: the CMS fan-out, the **`sqldoc access` suite against a real Active Directory**, and multi-tenant mode. No new features, no breaking changes; **+241 tests (1205 → 1446)**. Full detail in `CHANGELOG.md`.

**The unifying failure mode across all of it was *silent wrongness*** — sqldoc exited 0 and produced a report that looked complete and correct while being neither. That is the thing to keep hunting.

- **`driver:` was ignored at 9+ call sites** — CMS (`connection_string_for`/`connect_cms`/`discover_live`/`_adapter_for`), `agent/cms_monitor`, `agent/config` (incl. `agent.cms` never inheriting the top-level key, which made the monitor fix inert), `cli._adapter_from_db_entry` / `load_tenants` / `_load_cms_inventory` / `run_cms_bulk` / `_cms_opts`, and the whole access suite. On a Driver-17-only host every one of those features failed **despite correct config**, while `doctor` recommended the exact fix they ignored. **Root cause: `driver` must be threaded manually to every call site, so each new site is a fresh chance to forget — a single resolved connection-settings object would make this structurally impossible. Prefer that if this area is touched again.**
- **New `adapters.build_connection_string_for(dialect, …)`** — non-SQL-Server dialects configured with discrete `server`/`username`/`password` were handed a **SQL Server ODBC string**. It routes to the matching adapter and gates `windows_auth`/`driver` to the SQL Server family (incl. MI + Synapse). **Use this, not `build_connection_string`, wherever a dialect is in play.**
- **Config discovery** — `.sqldoc.yml` was read only from the cwd, so running from a subdirectory silently dropped every setting (symptom: a bare ODBC `IM002` that never mentioned the config). Added git-style parent search (`cli.find_config`), with the resolved path echoed so a parent config is never adopted silently.
- **`IM002` now explains itself on every connecting command** — names the driver requested, the config in effect (or that none was found and where it searched), and the fix. Shared `cli._abort_connection_failed` replaced 17 byte-identical local handlers (doc/scan/health/quality/intel/insights/comply/server/logs/secure/waits/ha/deadlocks/plans/baseline/executive/backup), plus `_run_integration`, a once-per-run hint in `comply --all-databases`, and `cms discover`. **Any new connecting command must route through `_abort_connection_failed`** — a structural test in `tests/test_driver_override.py` enforces that the bare `Connection failed: {e}` pattern never returns.
- **`executive` scored stale backups as 100% compliant** — `backup_compliance` never checked age, so a FULL-recovery DB with current log backups and a **two-year-old** full backup raised no rule. Now reuses `backup.stale_databases()` with a shared `backup.DEFAULT_MAX_BACKUP_AGE_HOURS` (24 h, matching the agent alert), matching entries by identity so a repeated name cannot miscount.
- **Access-suite correctness (the largest class — see "Access: group-based is the primary path" below).** A `sysadmin` was reported as having **no access** (it has no database principal, so `collect_db_access` skipped it); `securityadmin` / `CONTROL SERVER` / `ALTER ANY LOGIN` / privileged `IMPERSONATE` were unmapped; `GRANT CONTROL ON DATABASE` was *structurally* unreturnable (`DB_PERMISSIONS_SQL` filtered `class = 1` and inner-joined `sys.objects`); nested AD groups were invisible (**48 seen vs 213 actual**); `access check` printed a green all-clear having contacted nothing; `access request` claimed access while listing none; `access script` picked the **sysadmin group** as a read-grant target; and `access review` flagged `NT SERVICE\MSSQLSERVER` as orphaned with a generated **`DROP LOGIN`** fix (**6 of 25 findings**). `TAKE OWNERSHIP` is recorded on a new `DatabaseAccess.flags` field as an escalation *route*, deliberately **not** levelled.
- **`access.servers` accepts `windows_auth:` + `driver:`**, inherited from the top level. Inheritance tests **`is None`, not falsiness**, so an explicit per-entry `false` still overrides a global `true` — preserve that when touching inheritance.
- **Passwordless Kerberos LDAP bind** — `access.ad.windows_auth: true` binds over SASL/GSSAPI as the current Windows session, no stored password. Never inherits over an explicit `bind_dn`. Needs `winkerberos` (Windows) / `gssapi` (else), now declared in the `activedirectory` extra with environment markers. **ldap3's NTLM cannot use the current Windows session** (it computes from a supplied password/hash, never calls SSPI) — do not document NTLM as an integrated-auth option.
- **Report contract change (deliberate):** `access-check` JSON gained `access[].flags` and `logins[].server_permissions`, and `access/render.py` gained **Server-level privileges** + **Escalation routes flagged** sections. Both fields were collected and displayed nowhere, which made server-scoped grants and escalation routes invisible. The pinned key sets in `tests/regression/test_contracts.py` were updated, and `logins[]` is now pinned too.
- **`cms discover` announces its write** — it persists the whole estate inventory to `.sqldoc.yml` unless `--no-save` (in validation: **159 hostnames, 34 groups, ~25 KB** on first run, notice only *after* the fact). It now names the destination and counts *before* writing. **Inverting the default to opt-in `--save` is a breaking change deferred to a future major version** — still worth doing.

### Access: group-based is the primary path, not an edge case
**Confirmed against a real enterprise directory + SQL Server estate**, and the reason every v3.0.4 access bug shared one failure mode (*reporting "no access" for a principal holding full control*). In large enterprises the model is *purely* group-based: users are members of role groups (`G-` here), SQL logins are Windows **groups** (`D-` here), joined by **nesting** (`user → G-Role → D-Resource`, only `D-Resource` existing as a login) — and **there are no individual user logins in SQL Server at all.** Individual-login matching is the rare case. Treat group-based resolution as the main path in every correctness decision.
- **Do not introduce prefix-based (`G-`/`D-`) heuristics** — conventions differ per organisation. `_name_part()` (strips `DOMAIN\`, compares case-insensitively) is correctly naming-agnostic; keep it that way.
- **Keep surfacing the resolution chain.** `via` now reads e.g. `group DOMAIN\D-Resource -> server-wide sysadmin`. That is what made these bugs diagnosable at all — extend it, do not simplify it away.
- **Still untested:** multi-level nesting >2 deep against a real directory; `DOMAIN\Group` vs bare `Group`, CNs with spaces or escaped backslashes, NetBIOS vs FQDN mismatches between AD and SQL.
- **`review` / `recommend` / `intake` / `jira` share `build_db_adapter` + `collect_db_access`** and inherited all of these bugs. Only `check`, `request`, `script` and `review` were exercised — the rest deserve a dedicated validation run.
- **Orphan detection still ignores WINDOWS_GROUP logins** — `review_logins` gates on `"WINDOWS_LOGIN" in lg.type`, so group logins are never checked for a backing directory object. In a group-based shop that inverts the feature's value: an orphaned `D-` group login (AD group deleted, SQL login left) is the *primary* orphan risk and is currently undetectable. Fixing it needs a `get_group(identifier) -> ADGroup` added to all seven identity sources, defaulting to **"unknown" (never "not found")** so sources that cannot answer generate no false positives — the exact failure mode that made the built-in-principal bug so damaging. Keep the built-in-authority skip applied to both paths.

### v3.0.3 — real-world enterprise hardening (300M-row corporate SQL Server)
The **first release driven entirely by running sqldoc against a real corporate database** — 671 tables, ~300M rows, on the day-job work laptop. Four field-fix patches; no new features, no breaking changes.
- **Quality connection resiliency** — `collect_quality` now detects a dropped connection and reconnects (`_is_connection_lost` / `_reconnect`) instead of cascading one transient TCP blip into thousands of "communication link failure" skips and a silently-incomplete report. An unrecoverable loss records one honest summary error and stops.
- **Large-table safety** — row-count guards on every heavy aggregate, with `APPROX_COUNT_DISTINCT` used where the engine supports it (runtime-probed via `_detect_approx_distinct`) for duplicate detection and heavy per-column stats; otherwise the stat is skipped with a visible note. New flags `--duplicate-max-rows` / `--heavy-stats-max-rows` (default `5_000_000`, `0` = unlimited). **Observed failure this fixed:** `quality` stalled ~30 min on schema tables of 60–123M rows, silently, because per-item `try/except` swallowed the stall.
- **Backup database default** — corrected default database selection for `backup`.
- **This is now a standing architectural rule, not a one-off fix** — see the **"Large table safety"** section below. Any future feature that scans or aggregates *actual row data* must carry a `--<name>-max-rows` guard + graceful degradation. New tests: `tests/test_quality_large_tables.py`.

**Takeaway for planning:** the mock + Docker suites found *zero* product bugs across v2.8.0's whole testing push, but one afternoon against a real 300M-row corporate estate found four. Real-world enterprise testing is the highest-yield activity available right now — hence the next-session plan below.

4. **Handling the PAT — read this before asking Claude to push (learned twice, 2026-07-22 and 2026-08-13).** The `!` prompt prefix runs **bash/git-bash**, not PowerShell. Writing the token to a file from that prompt (`printf '%s' 'TOKEN' > …`) **does not help** — the literal value sits on the command line and is recorded in the transcript verbatim. **Create the token file in a separate terminal or an editor, outside the session, then hand over only the path.** Any token typed into a `!` line is burned; revoke it. Prefer **minimal scope** — a fine-grained PAT with just `Contents: Read and write` on `htamber1/sqldoc`, short expiry; a broad classic token (`admin:org`, `delete_repo`, …) in a chat log is a much worse outcome than the same mistake with a narrow one.
   - **PAT push diagnostics** (cost three round-trips on 2026-08-13): `GET /repos/:o/:r` returning `"push": true` is **misleading** — it reports the account's role, not the token's grants. Fine-grained PATs need `Contents: Read and write`; read-only passes `GET /contents/...` but push 403s. Non-mutating write probe: `POST /git/refs` with an *existing* ref + its current sha → 422 = write granted, 403 = not; the `x-accepted-github-permissions` response header names exactly what's required. If the pushed commits touch `.github/workflows/`, `Workflows: write` is needed too — check with `git diff --name-only <remote-sha> <local-sha> | grep '^\.github/workflows/'` *before* requesting permissions. Classic-token scopes show up in the `X-OAuth-Scopes` header on `GET /user`.
   - **One-shot push that stores nothing:** `git -c credential.helper= push "https://x-access-token:${TOKEN}@github.com/htamber1/sqldoc.git" main <tag>`. Leaves `origin` clean. Note it does **not** update `refs/remotes/origin/*`, so the branch still reads "ahead 1" — run `git fetch --tags origin` afterwards to resync.

## Large table safety

Enterprise SQL databases routinely contain tables with **50–150 million rows**
(logging, metering, monitoring, event/outbox tables, etc.). On such tables an
unbounded full-table scan or aggregate does not merely run slowly — it can run for
**hours** or appear to hang. And because sqldoc wraps per-item work in
`try/except`, the failure is *silent*: the run stalls, or the report looks
"complete" while missing data. This was observed live during dev-server validation
against a 671-table / 300M-row corporate SQL Server: `quality` stalled for ~30 min
on schema tables of ~60–123M rows (fixed by the guards below).

**Rule:** any query that performs a full-table scan, or a full-table / all-column
aggregate over **actual row data**, MUST have a **row-count guard** with a
**configurable threshold** (default `5_000_000`; `0` = no limit) and **graceful
degradation**. This applies to — but is not limited to:

- `COUNT(DISTINCT col)` — sort/hash of all distinct values.
- `GROUP BY <all columns>` — full-row duplicate detection.
- `GROUP BY col ORDER BY COUNT(*)` — top-N value distributions.
- `MIN(col)` / `MAX(col)` on unindexed or large columns.
- any new profiling, sampling, or data-analysis query that reads row data.

**Degradation, in priority order:**
1. **Approximate** when the engine supports it — e.g. SQL Server 2019+
   `APPROX_COUNT_DISTINCT`, PostgreSQL `hll`. **Detect the capability at runtime**
   (server version / extension presence); never assume it exists.
2. Otherwise **skip** the heavy stat and record a clear, user-visible note
   (`"n/a (table too large)"` / `"skipped — table too large …"`) in
   `report.errors` — it renders in the report's "Skipped" section and in JSON.
3. Always keep the cheap, bounded stats (row count, null count) running.

**Threshold plumbing (established pattern — reuse it):**
- A `--<name>-max-rows` CLI option: `click.IntRange(0, None)`, default
  `5_000_000`, `0` = unlimited; resolved through the config resolver like the rest,
  and registered in `CONFIG_KEYS` so it is also settable from `.sqldoc.yml`.
- Passed into the `collect_*` function as `<name>_max_rows`.
- The guard compares the table's **extracted `row_count`** to the threshold
  **before** issuing the query. A falsy threshold (`0`/`None`) disables the guard.

**Dialect awareness:** capability differs per engine. Encode the approximate SQL
plus a capability probe on each dialect profile; default to *skip* for engines
without a safe approximation (MySQL, SQLite) rather than emitting an expensive
query that hangs again.

**Precedent in the codebase** (`sqldoc/quality.py`):
- `detect_duplicates(..., row_count, max_rows)` → `_DUP_SKIPPED_TOO_LARGE` sentinel skip.
- `analyze_column_quality(..., row_count, heavy_max_rows, approx_distinct_ok)`
  and `_detect_approx_distinct()` (runtime `APPROX_COUNT_DISTINCT` / `hll` probe).
- CLI flags `--duplicate-max-rows` and `--heavy-stats-max-rows`.

Related: `collect_quality` also **reconnects on a dropped connection** rather than
cascading one transient TCP blip into thousands of "communication link failure"
skips and a silently-incomplete report (`_is_connection_lost` / `_reconnect`; an
unrecoverable loss records one honest summary error and stops).

**Every current and future feature that profiles or analyzes actual row data must
follow this pattern.** When adding such a feature, add its threshold option, wire
the guard, and degrade gracefully — do not ship an unbounded aggregate.

## Running

Packaged with `pyproject.toml` (setuptools); `pip install .` (or `-e .`) installs the **`sqldoc`** console command (entry point `sqldoc.cli:main`). You can still run it as a module from the repo root using the checked-in venv:

```bash
venv/Scripts/python.exe -m sqldoc.cli --server <host> --database <db> --username <user> --password <pw> --output docs.html
```

Key options (see `sqldoc/cli.py`):
- `--mode local|cloud` — `local` (default) calls Ollama at `http://localhost:11434`; `cloud` calls the Anthropic API.
- `--model` — model name. **Default is `None` and resolved per-mode** in `main()`: `llama3.1:8b` for local, `claude-haiku-4-5` for cloud. This split exists so the local Ollama tag never leaks into a cloud API call. Explicitly passing `--model` overrides for whichever backend is active; it is threaded all the way through to `_call_anthropic(prompt, model)` / `_call_ollama(prompt, model)`.
- `--no-ai` — skip all LLM calls, emit schema-only docs. Use this to iterate on extraction/rendering without a running LLM (also the fastest smoke test of the CLI plumbing).
- `--schemas` — comma-separated schema allowlist; filtering happens in `cli.py` *after* full extraction, and applies to tables, views, and procedures alike.
- `--concurrency` — parallel AI calls during enrichment (1-64, default 8). Threaded to all three `enrich_*` functions, which run their per-object calls through a `ThreadPoolExecutor`.
- `--connection-string` — full ODBC connection string as an alternative to `--server/--database/--username/--password`; takes precedence over them. The database name is parsed out (`DATABASE=`/`Initial Catalog=`) for labeling + snapshot/cache filenames. The extractor now takes a single connection string (`build_connection_string()` assembles it from parts).
- `--cache` / `--no-cache` — AI description cache (default `.sqldoc-cache/<database>.json`). Reuses descriptions for objects whose structural signature is unchanged; gitignored.
- `--config` — path to a `.sqldoc.yml` (default `.sqldoc.yml` in cwd if present). Any option can be set there; an explicit CLI flag overrides the config, which overrides the built-in default. Connection flags are optional when supplied via config.
- `--yes` / `-y` — bypass the cloud confirmation prompt (below) for non-interactive/CI runs.

**Privacy posture — local-first by design.** Local mode is the default; nothing leaves the network unless `--mode cloud` is explicitly chosen. The banner prints a `Privacy:` line stating the egress posture every run. `--mode cloud` additionally prints a warning and blocks on an interactive `click.confirm` (defaults to "no") before any network call — `--yes` skips only the prompt, not the warning. Note the data boundary: **only schema metadata** (table/column names, types, keys, row counts, existing `MS_Description` text) is ever sent to Anthropic — the extractor queries only `sys.*` catalog views and never reads table row data.

`--mode cloud` needs `ANTHROPIC_API_KEY`, loaded from `.env` via `python-dotenv` (`load_dotenv()` runs at import in `cli.py`).

## Architecture

A linear pipeline, one module per stage, orchestrated by `cli.py`:

1. **`adapters/` + `extractor.py`** — the metadata-extraction layer. **`adapters/base.py`** defines the shared-currency dataclasses (`Table`, `Column`, `Index` attached to a `Table`, `View`, `Parameter`, `StoredProcedure`), a `Capabilities` advertisement, and the `DatabaseAdapter` ABC. **`adapters/sqlserver.py` `SqlServerAdapter`** is the DB-facing code today: `extract_metadata()` queries `sys.*` catalog views (tables + row counts, a per-table `sys.columns` join for PK/FK/`extended_properties`=`MS_Description`, and a per-table `sys.indexes`/`sys.index_columns` query grouping key vs included columns); `extract_views()`/`extract_procedures()` add views (with `sys.sql_modules.definition`) and procedures (with `sys.parameters`). Any real `MS_Description` is captured here — the AI stage only fills descriptions left empty. **`extractor.py`** is a thin back-compat shim re-exporting the dataclasses + `build_connection_string`/`get_connection`/`extract_*` (delegating to `SqlServerAdapter`); `adapters/__init__.py` `get_adapter(cs, dialect)` picks the adapter by `--dialect`/auto-detection. NOTE: `health`/`quality`/`comply`/`pii` still run their own dialect-specific SQL via `extractor.get_connection` (see the "deferred" note in the v1.5.0 plan).

2. **`ai.py`** — `enrich_tables()`/`enrich_views()`/`enrich_procedures()` mutate the objects in place, setting `.description`. Two backends behind a `mode` switch: `_call_ollama` (HTTP to localhost) and `_call_anthropic` (SDK, shared lazily-created client, default model `claude-haiku-4-5`). Each `enrich_*` builds a flat list of independent per-object work units and runs them through a `ThreadPoolExecutor` (`--concurrency`, default 8) — each unit writes only its own object's `.description`, so there is no cross-thread shared state. View/proc prompts are **metadata-only** (names + columns/params, never the SQL definition) to keep the cloud data boundary unchanged.

3. **Renderers (one per format, same signature `(database, tables, output, views, procedures)`)** — `cli.py` picks one from `--format`/extension:
   - **`renderer.py`** `render_html()` — groups each object type by schema and renders the single `HTML_TEMPLATE` via an **autoescaping** Jinja `Environment` (all CSS inlined) to one standalone file. Autoescaping matters: view/proc definitions contain `<`/`>`/`&`.
   - **`markdown_renderer.py`** `render_markdown()` — single `.md` for GitHub wikis (TOC + anchor links, escaped table cells, fenced SQL).
   - **`pdf_renderer.py`** `render_pdf()` — `fpdf2` multi-page PDF; imported lazily so the other formats don't require it; Latin-1 text sanitization.

4. **`snapshot.py`** — orthogonal to rendering. `build_snapshot()` serializes the schema **structure** (not descriptions/rows) to JSON; `diff_snapshots()` + `iter_diff_lines()` produce the git-diff-style change report that `cli.py` prints (colored) and then re-saves the snapshot. Runs after schema-filtering, before enrichment, so it works with `--no-ai`.

5. **`pii.py` + `pii_renderer.py`** — the `sqldoc scan` path (independent of the doc pipeline; reuses `extract_metadata`). `pii.py` holds the `PII_CATEGORIES` catalog (name patterns → severity + regulations + action), a camelCase-aware matcher (`\b` patterns match tokenized names, others match the compact name), `scan_tables()` → `Finding`s with risk/confidence, and `confirm_with_sampling()` (opt-in `--sample`: reads ≤5 values per column, AI-confirms, **never stores samples**). `pii_renderer.render_pii_html()` writes the compliance report (dashboard, risk filter, CSV export via `tojson`). If you add a PII category, edit only `PII_CATEGORIES`.

The dataclasses flow through unchanged: extractor builds them → ai enriches them → renderers read them. If you add a **field**, touch the extractor, `ai.py` (if it needs a description), **all three renderers**, and `snapshot.py` (if it's a structural field worth diffing). If you add a new **object type**, also thread it through `cli.py` (extract → schema-filter → snapshot → enrich → render).
